# Four reviews. Three products grow.

Keep an **individual game**, **shared customer project** and **personal portfolio**. The future review dates, points and submission boxes remain **planned until posted in Canvas**. The current RPS-001 grade and rubric are unchanged.

## What each review adds

| Review | Creative game | Group customer project | Portfolio |
| --- | --- | --- | --- |
| **1 · Plan** | Two concepts; required account/game promise; stack, stories and architecture. | Select a prepared customer; discovery, two proposals, agreed small workflow and work split. | Three role cards, two career directions, audience/persona, two brand/layout directions and a short spec. |
| **2 · First slice** | Accounts, one correct saved game and focused tests/design experiment. | One real workflow slice; actual member contributions and cross-review. | A readable draft with two lightweight presentation options; résumé/profile/repository links. |
| **3 · Integrated build** | Private scores/dashboard, account maintenance, ownership and regression checks. | Integrated workflow; respond to the simulator's bounded change; real peer observation. | Chosen presentation, accurate project evidence and working professional links. |
| **4 · Improve/handoff** | Peer issue → change → retest; setup, CI and AI-learning note. | Peer issue → change → retest; customer acceptance comparison, handoff and each person's work. | Peer issue → change → retest; finished site, résumé, GitHub/LinkedIn and honest case studies. |

Compare two options where the decision matters. Shared code, content and assets are fine. You do not need two full game backends or two independent portfolio sites.

## One small hand-in per product

Update the same record for each product. Link the current revision/demo, relevant issue/PR and actual checks. Add **what changed, what was checked and what is next**. A Studio can point to the same game evidence; no duplicate report or prompt transcript is needed.

Example receipt:

```text
Product: creative game · Review 2 / Studio 002
Revision/demo: [actual links]
Spec + account/game stories: [same record]
Tests + CI: [actual result links; name anything not run]
Issue/PR: [actual links]
Changed / checked / next: three short notes
```

The group keeps one shared record and identifies each person's design, implementation and QA. The portfolio's career/design notes live with that project; private reflection can be submitted through the instructor's stated private route. Follow Canvas for the actual submission settings.

## Proposed example rubric {#how-the-worked-examples-are-assessed}

The worked examples use **25 points per row**. Canvas must publish any adopted future rubric before grading. This does not set course category weights.

| Criterion | Evidence |
| --- | --- |
| **Complete · 25** | The stage's required scope is supplied: game/account journey, agreed customer workflow or portfolio requirements. |
| **Thoughtful · 25** | Audience, two alternatives and a justified design/architecture decision. Creativity serves a purpose. |
| **Checked · 25** | Actual checks suited to the product, real peer observation, change and retest. Simulated customer dialogue is labeled. |
| **Understood · 25** | Your contribution, reasoning, accurate claims and what you learned from agent output. |

For software, include meaningful automated and integration checks plus an actual pattern experiment. For the portfolio, use reader tasks, link/mobile/keyboard checks and accurate career/project evidence. A static portfolio does not need a database or a game-style design pattern.

An optional experiment can fail and still show judgment. Required behavior still needs repair. Fictional peer stories and unrun tests cannot earn execution credit.
