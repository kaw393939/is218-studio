# What to hand in

**Update the same record for each active project.** Send the links requested by its Canvas assignment:

- Your current work and source repository.
- The short project record.
- A useful issue/change link and what you checked.
- A few lines: **changed / checked / next**.

The group shares one record and names each person's work. A Studio can use the same game evidence. Keep private career reflections in the instructor's private submission route.

**See the size to aim for:** [short update example](/examples/). [Your next class](/course/schedule) has the current task and date.

## Published project-review rubric {#how-the-worked-examples-are-assessed}

The published final-project review assignments use **25 points per row**. The worked examples illustrate those four criteria; their fictional scores are not student grades. Follow Canvas for the required scope, dates and points. This does not change course category weights or the earlier RPS-001 rubric.

| Criterion | Evidence |
| --- | --- |
| **Complete · 25** | The stage's required scope is supplied: game/account journey, agreed customer workflow or portfolio requirements. |
| **Thoughtful · 25** | Audience, two alternatives and a justified design/architecture decision. Creativity serves a purpose. |
| **Checked · 25** | Actual checks suited to the product, real peer observation, change and retest. Simulated customer dialogue is labeled. |
| **Understood · 25** | Your contribution, reasoning, accurate claims and what you learned from agent output. |

For software, include meaningful automated and integration checks plus an actual pattern experiment. For the portfolio, use reader tasks, link/mobile/keyboard checks and accurate career/project evidence. A static portfolio does not need a database or a game-style design pattern.

An optional experiment can fail and still show judgment. Required behavior still needs repair. Fictional peer stories and unrun tests cannot earn execution credit.
