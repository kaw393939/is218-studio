# Keep track of the improvement

Use an issue in **your project repository** for a feature or useful piece of feedback.

1. Say what should happen and what needs changing.
2. Make the change. Include the issue number in the commit message, such as `Make the result clearer (#12)`.
3. Check the result, link the change and close the issue when it is resolved.

## Review research before building

Present the two individual research sites to a partner. The reviewer should be able to find the question, original sources and dates, evidence versus assumptions, alternatives, chosen reason and next experiment without reading an AI chat transcript. Trace one source → observation → decision → story/check. Check an original source together and ask what would change the decision.

For a useful finding, open an issue in the affected site's repository with the page/claim, evidence, impact and proposed next step. The author records a decision, links the documentation/code change, verifies it against the source or task, and resolves the issue with the actual result. A reasoned disagreement can be recorded with evidence; do not close an unresolved defect as fixed. Label pending checks honestly. This adds no issue quota and does not replace existing project review requirements.

For group work, name an owner and ask someone else to try the result. Record what actually happened. Keep required pull requests, reviews and CI checks from the posted Studio instructions.

```text
Task: A new user can find the next step.
Change: [commit or PR link]
Check: [who tried what, on which version, and what happened]
```

Put the issue link in the same project record. Canvas is where you submit coursework and receive grades. Private circumstances stay there too.
